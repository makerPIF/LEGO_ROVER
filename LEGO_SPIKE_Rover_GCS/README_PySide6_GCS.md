# SPIKE Rover GCS — tunnel-v2 (2026-09-21)

## 이번 로그가 보여주는 것

사용자가 보낸 로그에서 연결, 알림 등록, InfoRequest/InfoResponse는 성공했습니다.
RPC 1.0.47 / FW 1.8.149가 확인됩니다. 따라서 BLE 자체가 전혀 통신하지 못하는 상태는 아닙니다.
하지만 `Q 전송 요청`은 허브의 응답이 아닙니다. 실제 Q ACK는 화면에 보이지 않습니다.
앞선 GCS는 Q ACK가 없으면 키보드/패드 주행 명령을 차단하므로, 이 상태에서 WASD가 동작하지 않는 것은 예상되는 결과입니다.

`#T`는 기본적으로 로그에 모두 표시하지 않으므로 이 스크린샷만으로 텔레메트리 부재나 허브 프로그램 정지를 확정할 수는 없습니다.
이전 연결이 20.7초 만에 끊긴 기록도 있지만, 재연결 이후 기록만으로 전원 꺼짐이 해결됐다고 말할 수는 없습니다.

## 핵심 수정: stdin 가정을 제거하고 BLE 터널 API 연결

앞선 수정본은 안전장치와 수신 프레임을 보완했지만 핵심 수신 경로를 놓쳤습니다.

| 구간 | 앞선 구현 | tunnel-v2 |
|---|---|---|
| 허브 명령 수신 | `sys.stdin.read()`만 사용 | `hub.config['module_tunnel'].callback(...)`에 수신 함수를 등록 |
| 허브 응답 송신 | `print()`만 사용 | `module_tunnel.send()`로 ACK와 텔레메트리 송신 |
| PC 응답 처리 | 콘솔 알림 0x21 등만 해석 | 터널 메시지 0x32의 길이를 검사한 뒤 payload 해석 |
| 텍스트 버퍼 | 콘솔 단일 버퍼 | 콘솔/터널 버퍼를 분리하여 부분 문자열 혼합 방지 |
| 키보드 | 창의 keyPressEvent에만 의존 | 버튼/슬라이더가 포커스를 가져도 앱 이벤트 필터에서 입력 처리 |
| 업링크 진단 | Q 전송 요청 안내만 표시 | 텔레메트리 유무 → BLE 쓰기 완료 → ACK 성공/시간 초과를 구분 |

LEGO 개발자는 공식 저장소의 이슈 답변에서 실행 중인 프로그램과 PC 간 통신에 별도의 터널 API가 있다고 설명합니다. 해당 이슈에 소개된 공개 구현에서 `hub.config['module_tunnel']`의 `callback`과 `send` 사용을 확인했습니다.

이 API는 공개 Python 교육용 API와 같은 수준으로 안정성이 보장된 인터페이스라고 가정하지 않습니다. **사용자 FW 1.8.149에서 실제 실행 검증을 마친 것은 아닙니다.** 이번 버전은 존재 여부와 콜백 등록 오류를 확인하고 로그로 보고합니다.

기존 `TunnelMessage → stdin` 경로가 모든 펌웨어에서 된다고 가정하지 않습니다. BLE에서는 터널 콜백을 우선 사용하며, stdin은 터널 API가 없는 환경의 별도 fallback일 뿐입니다. 기본 터널 모드에서 USB 텍스트 조종을 동시에 제공하지 않습니다.

## 반드시 허브와 PC 모두 교체

압축 파일을 새 폴더에 풀어 사용하세요. 제목에 **SPIKE Rover GCS — tunnel-v2**가 표시돼야 합니다.

- `hub_rover.py`: 허브에 업로드. 파일 첫 부분에 `tunnel-v2` 표기.
- `rover_gcs.py`: PC GCS.
- `requirements.txt`: PC 의존성.
- `test_regression.py`: 장비 없는 회귀 테스트.

```bash
python -m pip install -r requirements.txt
python rover_gcs.py
```

1. 바퀴를 띄우고 좌/우 모터 포트를 확인합니다. 기본값은 A/B입니다. 다르면 허브 코드의 `LEFT_PORT_ID`, `RIGHT_PORT_ID`를 먼저 맞춥니다.
2. SPIKE App 3에서 새 Python 프로젝트를 만들거나 기존 프로젝트 내용을 모두 교체하여 **이번 hub_rover.py 전체**를 넣습니다.
3. 허브의 원하는 슬롯에 다운로드하고 슬롯 번호를 확인합니다. 파일 이름만 바꾸는 것으로는 허브 프로그램이 갱신되지 않습니다.
4. SPIKE App을 종료합니다. 허브에서 다운로드한 프로그램을 실행합니다.
5. 새 GCS에서 스캔 → 선택 → 일반 연결합니다. 안전 모드/링크 시험 모드는 조종용이 아닙니다.
6. 응답이 없으면 GCS의 슬롯을 맞춘 다음 [프로그램 시작]을 누릅니다. 슬롯 번호가 맞는지 반드시 확인합니다.
7. [업링크 진단]을 누릅니다. 정상이라면 아래와 같은 로그가 나타납니다. 순서는 달라질 수 있습니다.

```text
허브 → GCS 터널 수신 확인 (0x32)
허브: version=tunnel-v2,mode=tunnel
◆ 허브 수신 계측: rx=...,ln=...,last=Q,mode=tunnel
Q BLE 쓰기 완료 — 허브 ACK 대기
허브: ack=Q
업링크 성공: 허브가 Q를 해석하고 ACK를 응답했습니다.
```

8. 상단 `조종 준비 완료`와 약 4Hz를 확인하고 포트/반전 설정을 적용합니다.
9. 방향 패드를 짧게 누른 다음 WASD를 시험합니다. 명령 입력창이나 숫자 입력칸을 편집 중이면 키보드 조종은 동작하지 않습니다. 패드를 클릭한 뒤 키보드를 사용하세요.
10. 버튼/키를 놓으면 정지하는지, Space로 정지하는지 확인합니다.

허브 코드를 교체하지 않으면 이번 수정 효과가 없습니다. PC 코드만 교체하지 마세요.

## 여전히 응답이 없을 때 보는 로그

| 메시지/상태 | 의미와 다음 확인 |
|---|---|
| InfoResponse만 있음 | 펌웨어 RPC 통신은 가능. 사용자 프로그램의 실행/출력 여부는 별도 확인 |
| 프로그램 요청 ACK | 시작 요청 접수. 사용자 프로그램의 정상 실행까지 보장하지 않음 |
| 프로그램 요청 거부됨 | 슬롯/프로그램 저장 상태를 SPIKE App에서 확인 |
| `module_tunnel_unavailable` | 이 실행 환경에서 `hub.config['module_tunnel']`을 얻지 못함. 오류 전문 필요 |
| `tunnel_callback` 오류 | API는 있으나 callback 등록 실패. 오류 전문 필요 |
| `version=tunnel-v2,mode=tunnel` | 새 허브 코드의 터널 콜백 등록 성공 |
| `Q BLE 쓰기 완료`만 있음 | PC BLE API에 쓰기 완료. 허브 명령 해석까지 확인된 것은 아님 |
| `ack=Q` 있음 | 허브 프로그램까지 명령이 도달하고 응답도 돌아옴 |
| `pair_fail` / `drive` 오류 | 모터 포트·케이블·motor API 오류를 확인 |
| 방향 패드는 동작, 키보드만 실패 | 텍스트/숫자 입력칸의 포커스를 벗어나 사용. 실행창 제목이 tunnel-v2인지 확인 |

새 진단 결과는 2.5초 후 표시됩니다. 원인을 단정하지 않고 응답이 끊기는 단계를 구분합니다.

## 안전장치

- 터널 callback 안에서는 모터를 돌리지 않고 받은 바이트만 제한된 큐에 복사합니다.
- 제어 루프가 명령을 해석하고 실행합니다. 큐가 넘치면 E 정지로 전환합니다.
- 주행 T 갱신이 800ms 넘게 끊기면 주행·자세유지·보조모터 정지. 실제 반응 시간에는 20ms 제어 주기와 실행 지연이 추가됩니다.
- 보조모터는 각 포트의 A 명령 갱신도 독립적으로 감시합니다.
- E 이후 T0,0 유지 전송은 비상정지를 해제하지 않습니다. 새 비영 T 입력으로 주행을 재개합니다. 물리적인 래치형 비상정지 장치는 아닙니다.
- 연결/프로그램 시작만으로 자동 전진하지 않습니다.
- 포트를 바꾸기 전에 기존 모터를 정지하고 좌우 중복 포트를 거부합니다.
- 앱이 비활성화되면 정지 요청을 보냅니다. 허브 자체 워치독도 유지합니다.

## 테스트 범위

Python 문법 검사와 장비 없는 회귀 테스트 **20개 통과**.

```bash
python -m py_compile rover_gcs.py hub_rover.py test_regression.py
python test_regression.py
```

기존 프레임/정지 테스트 12개에 추가하여 실제 수정 소스의 callback → 명령 파서 → send → COBS 패킷 → GCS 수신 파서의 Q 왕복, 주행/정지, 콜백 내 비구동, 잘못된 길이 거부, 터널 텔레메트리, 큐 넘침 정지, 분할 명령, 콘솔/터널 버퍼 분리를 검증했습니다.

모의 장치 검증입니다. 실제 허브 FW, BLE 드라이버 및 PySide6 GUI 실행 검증은 포함하지 않습니다.

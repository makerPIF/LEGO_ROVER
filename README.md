# SPIKE Prime 탐사로버 GCS — 최종 정리본

## 결론부터: 무엇이 되고 무엇이 안 되는가

| 경로 | 조종 | 텔레메트리 | 상태 |
|---|:--:|:--:|---|
| **USB 케이블** | **✅** | **✅** | **정상 동작 (영상으로 확인)** |
| Bluetooth (BLE) | ❌ | ✅ | 조종 불가 — 펌웨어 제약 |

**BLE로 조종이 안 되는 것은 설정 문제도, 코드 버그도 아닙니다.**
이 허브 펌웨어에는 BLE로 들어온 데이터를 실행 중인 파이썬 프로그램에
전달하는 경로가 구현되어 있지 않습니다. 측정으로 확정했습니다.

### 근거

허브 프로그램이 `sys.stdin`으로 받은 누적 바이트 수(`rx`)를 텔레메트리에
실어 보냅니다. BLE로 수백 번 명령을 보내는 동안:

```
#T,0.0,0.8,23.3,0,0,-20,115,-1,-1,-1,0,1149278,0
                                              └── rx = 0  (끝까지 0)
```

같은 시간에 이것들은 **정상 동작**했습니다.

- `ProgramFlowRequest` → `ProgramFlowResponse status=0` 수신 (프로그램 시작/중지)
- `ConsoleNotification` → IMU·센서 데이터 수신
- `select.poll` 등록 성공 (`mode=poll`) — 허브의 읽기 장치는 정상

즉 **받을 준비는 완벽한데 들어오는 것이 없습니다.** USB에서는 같은 코드,
같은 명령이 그대로 동작합니다. 차이는 전송 경로뿐입니다.

LEGO 공식 문서는 `TunnelMessage(0x32)`의 **구조만** 정의하고, payload가
허브 내부에서 어디로 가는지는 명시하지 않습니다. 실제로는 전달되지 않습니다.

### 허브가 꺼지는 현상

BLE에서만 발생합니다. 연결만 하면 30초를 버티고(`진단도구/ble_probe.py`),
알림을 켜서 **허브가 송신을 시작하면** 죽습니다. 송신은 수신보다 전류를
훨씬 많이 씁니다. 간헐적인 것도 전원 문제의 전형적 특징입니다.

30초 판별: **허브를 USB 충전기에 꽂은 채로 BLE 연결.**
안 꺼지면 배터리 문제 확정입니다(45610 팩은 소모품입니다).

## 실행 순서 (이대로 하면 됩니다)

### 1. 허브 준비 — 한 번만

1. SPIKE App 3 → 새 프로젝트 → **Python**
2. `hub_rover.py` 전체를 붙여넣기
3. 슬롯 확인 후 허브에 **다운로드**
4. **SPIKE App 완전 종료** (트레이 아이콘까지) ← 안 하면 COM 포트를 뺏깁니다
5. 허브 **가운데 버튼**으로 프로그램 실행

> USB로만 쓸 거면 `hub_rover.py`의 `TELEMETRY_MS = 250`을 `100`으로
> 바꾸세요. 10Hz로 부드러워집니다. (250은 BLE 부하를 줄이려는 값입니다)

### 2. GCS

```
pip install -r requirements.txt
python rover_gcs.py
```

기본 연결 수단이 **USB Serial**로 설정돼 있습니다.

1. 목록에서 허브 COM 포트 선택 → **[연결]**
2. 상단 **`허브RX`** 칩이 초록색으로 숫자가 오르면 정상
3. **W A S D** 로 주행 · `Space` 비상정지 · `G` 자세유지

### 3. 확인 지표

| 칩 | 의미 |
|---|---|
| `USB · COM26` 초록 | 연결됨 |
| `4 Hz` / `10 Hz` | 텔레메트리 수신 중 |
| `프로그램 실행중` | 허브 프로그램 동작 중 |
| **`허브RX 137`** 초록 | **명령이 허브에 도달 중** ← 핵심 |
| `허브RX 0` 빨강 | 명령이 안 닿음 |

`허브RX`가 오르지 않으면 조종이 안 되는 것이고, 오르는데 안 움직이면
모터·포트 문제입니다. 이 하나로 갈립니다.

## 무선이 필요하면

BLE는 이 펌웨어에서 막혀 있으므로, 선택지는 둘입니다.

**① ESP32 브릿지 (권장)**

```
GCS ──Wi-Fi──▶ ESP32 ──USB 시리얼──▶ 허브
```

지금 동작이 확인된 USB 경로를 그대로 무선화합니다. 허브 코드 수정이
필요 없고, ESP32-CAM 영상과 같은 Wi-Fi로 통합됩니다. USB 호스트가 되는
ESP32-S3 계열 보드가 필요합니다.

**② Pybricks 펌웨어**

PC↔허브 양방향 통신이 공식 지원 기능으로 문서화돼 있습니다. 브라우저에서
설치하고 언제든 LEGO 정품 펌웨어로 복원할 수 있습니다. 다만 SPIKE App 3
API(`motor_pair`, `runloop`)가 아닌 Pybricks API로 코드를 다시 써야 합니다.

## 통신 규약

**GCS → 허브**

```
T<좌>,<우>   주행 (deg/s)      S 정지            E 비상정지
H0 / H1      자세유지 OFF/ON   Y<각도> 목표방위   Z 기준각 리셋
K<kp>,<ki>,<kd>  게인(×1000)   V<최대속도>
A<포트>,<속도>  보조모터       P<좌>,<우> 포트지정
I<0|1>,<0|1>  좌/우 반전       L<문자> 매트릭스   Q 상태조회
!            모터 테스트 (0.8초 전진 후 자동 정지)
```

**허브 → GCS**

```
#T,yaw,pitch,roll,lvel,rvel,lpos,rpos,dist,refl,batt,hold,ms,rx
#I,...  정보      #E,...  경고      #S,...  수신 계측
```

GCS 아래쪽 **직접 명령 입력** 칸에 위 명령을 그대로 칠 수 있습니다.
`!` 하나만 보내면 모터가 0.8초 돌아 수신 경로를 가장 빠르게 확인합니다.

## 안전장치

- 허브 워치독 — 800ms 무통신 시 스스로 정지
- `Space` 비상정지 — 모터 coast + 모든 입력 초기화
- 프로그램이 실행 중일 때만 유지 전송 (빈 허브에 명령을 밀어넣지 않음)
- 가속도 제한 400 — 기동 전류 억제
- 안전 모드 연결 — 허브로 한 바이트도 보내지 않고 수신만

## 문제가 생기면

| 증상 | 원인 / 조치 |
|---|---|
| COM 포트가 안 보임 | SPIKE App이 트레이에 살아있음 → 완전 종료 |
| `PermissionError` | 같은 포트를 다른 프로그램이 점유 |
| `0 Hz`, 계기가 `--` | 허브에서 프로그램이 안 돌고 있음 |
| `허브RX 0` 빨강 | 명령 미도달 — USB인지 확인, `!` 직접 전송 |
| `#E,pair_fail` | A/B 포트에 모터 미인식 — 케이블 끝까지 삽입 |
| W가 안 먹음 | 창 빈 곳 클릭 후 재시도 (글자 입력칸 포커스) |
| BLE 연결 시 허브 꺼짐 | 배터리 — USB 전원 연결 후 재시도로 판별 |
